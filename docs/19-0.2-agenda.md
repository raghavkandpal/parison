# Parison 0.2 agenda

Date: 6 October 2026

## Goal

Turn Parison from a correct one-off comparison into a repeatable local and CI workflow, while expanding only the surfaces explicitly selected for 0.2.

The research recommendation remains evidence-first, but the project owner has chosen to include recipe generation, report filtering, and additional formats/connectors in the 0.2 agenda. Each item must preserve keyed-v1 semantics and remain independently shippable; one unfinished item must not force partial behavior into the others.

## Workstreams

### 1. Repeatable evidence in CI

- Add a tested GitHub Actions reference workflow.
- Preserve Parison exit codes after uploading every generated evidence bundle.
- Default to summary sensitivity and document public-fork/raw-artifact safeguards.
- Add concise terminal summaries without creating a second result model.

Done when an unfamiliar agent can integrate the workflow and a reviewer can retrieve, verify and interpret its bundle without maintainer help.

### 2. Recipe generation

- Add a command that generates a reviewable draft recipe from two inputs.
- Reuse exact shared column names and existing recipe validation.
- Require the user to choose keys, scope provenance, exclusions and any tolerance; never infer these as trusted policy.
- Mark unresolved choices explicitly and refuse comparison until the resulting recipe validates.

Done when two unfamiliar users can create valid recipes without copying JSON by hand, and the generator cannot silently create a false-PASS policy.

### 3. Static-report filtering

- Add dependency-free client-side filtering to the self-contained HTML report.
- Filter field summaries by classification and bounded raw samples by field, discrepancy class or key text.
- Preserve useful no-JavaScript content, keyboard access, escaping and summary-mode privacy.
- Do not turn the report into a local server, dashboard or persistent application.

Done when a reviewer can answer a seeded multi-field investigation task faster without changing the canonical result JSON.

### 4. Additional formats and connectors

- Deliver at least one additional local file format and one read-only local connector.
- Spike standard-library-first candidates: JSON Lines for the file format and SQLite for the connector.
- Define type mapping, snapshot/completeness assertions, row and byte limits, cancellation, and error behavior before accepting either implementation.
- Route all inputs through the existing comparison contract; do not expose backend-specific frames or invent a plugin system.

Done when mixed-input comparisons match an independent accuracy oracle and the new sources cannot weaken identity, null, tolerance, sensitivity or completeness semantics.

## Sequence

1. CI reference workflow and terminal summary.
2. Recipe generation.
3. Static-report filtering.
4. One additional format and one connector after their compatibility spikes pass.

Work may proceed in parallel only where result-schema and recipe-contract changes do not overlap. Keep each workstream in a separate reviewable change.

## Release gates

- Existing 0.1 bundles remain readable and verifiable.
- Existing outcome codes and keyed-v1 semantics do not change.
- All new branches, parsers and trust-boundary behavior have focused regression tests.
- Summary mode emits no source keys or raw values through terminal, report, logs or CI artifacts.
- The GitHub Actions flow is tested for PASS, FAIL, ERROR and INCONCLUSIVE; interruption is tested where deterministic.
- At least one unfamiliar agent completes each new workflow, followed by human review of its evidence.
- At least one target user repeats a comparison. Without repeat use, 0.2 may be technically complete but adoption remains unvalidated.

## Non-goals

- Hosted service, authentication, teams or remote artifact storage.
- Custom GitHub Action, bot or PR commenter.
- Automatic key, tolerance, exclusion or scope approval.
- Database writes, production credentials or network database connectors.
- UI framework, local web server or cross-bundle dashboard.
- Broad connector SDK or adapter/plugin abstraction.
- Changes to PASS, identity, null, tolerance or completeness semantics.

## Decision checkpoints

- After CI: confirm bundles survive nonzero outcomes and can be reviewed safely.
- After recipe generation: stop if drafts require as much manual correction as the existing example template.
- After report filtering: stop if seeded tasks show no measurable investigation benefit.
- After format/connector spikes: reject any source whose semantics cannot be mapped without backend-specific exceptions.

The agenda controls scope; it does not claim user demand. Findings in [the 0.2 product research](18-0.2-product-research.md) remain the evidence baseline.
