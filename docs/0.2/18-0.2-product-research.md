# Parison 0.2 product research

Research date: 6 October 2026

## Recommendation

Make 0.2 a **safe repeat-run release**, not a broader comparison engine.

The smallest coherent theme is: **make one reviewed recipe easy to run repeatedly in GitHub Actions while always preserving a verifiable result bundle**. Ship a tested starter workflow and a compact human-readable terminal summary; do not add new formats, connectors, history storage, or an interactive report in this release.

This recommendation is deliberately conditional. Repository evidence shows that an unfamiliar agent can run a supplied recipe and that a human can accept its evidence. It does **not** show that users want CI integration, that they struggle to author recipes, or that any proposed feature causes repeat use. Therefore 0.2 should be a bounded adoption experiment whose success criterion is actual reuse, not completion of a feature list. If no external user is ready to put the workflow into a second run or CI job, wait at `0.2.0.dev0` and collect evidence instead of manufacturing a roadmap.

### Owner scope decision

After reviewing this research, the project owner chose to include recipe generation, static-report filtering, and additional formats/connectors in the 0.2 agenda alongside the recommended CI work. That decision expands scope beyond the evidence-backed minimum; it does not convert the deferred-demand hypotheses below into observed demand. The bounded workstreams, sequence and stop conditions are recorded in [the 0.2 agenda](19-0.2-agenda.md).

## What the repository establishes

These are observations from Parison itself, not market claims.

- Version 0.1 already provides the semantic core: strict keyed CSV/Parquet comparison, explicit recipes, outcomes and exit codes, JSON/HTML evidence, integrity manifests, and summary-by-default data handling ([README](../../README.md), [built-evidence review](../0.1/14-built-evidence-review.md)).
- Two blinded agents correctly interpreted supplied recipes in different domains. One human accepted the second agent's recommendation and evidence. The only repeated execution deviation was packaging-related: the trials were not supplied a wheel and used the source tree instead ([unfamiliar-user protocol](../0.1/15-unfamiliar-user-test.md), [trial 02 score](../../studies/unfamiliar-user-02/agent-trial-01-score.md)). The published GitHub wheel now resolves that particular trial setup issue.
- The trials did not ask participants to create a recipe from their own files. Recipe-authoring friction is therefore plausible but unmeasured.
- The first rehearsal observed that `compare` prints only outcome and output path, while `validate-recipe` and `verify` print only `valid`. This was weak orientation, but it did not block either blind agent or the human reviewer ([unfamiliar-user protocol](../0.1/15-unfamiliar-user-test.md)).
- The static HTML report was sufficient for the two agent trials and the recorded human acceptance. There is no evidence of investigation friction that requires filtering or search ([built-evidence review](../0.1/14-built-evidence-review.md)).
- The delivery plan explicitly places a packaged alpha and safe CI examples in the repeat-adoption gate, and requires preservation of artifacts for exit codes `0`, `1`, `2`, `3`, and `130` ([validation and delivery](../0.1/09-validation-and-delivery.md)). That acceptance work has not been demonstrated in a consumer repository.
- Publication hardening remains incomplete: low disk, termination during final publication, and corrupted destinations are untested. The implementation writes into a sibling temporary directory and renames it only after completing the manifest, which is a sound starting structure, but it does not prove crash durability or low-disk recovery ([built-evidence review](../0.1/14-built-evidence-review.md), `publish` in [`src/parison/core.py`](../../src/parison/core.py)).
- No interviews, direct-human task comparison, real second use, or comparative time study exist. The repository therefore cannot support a claim that any 0.2 feature is demanded ([validation and delivery](../0.1/09-validation-and-delivery.md)).
- At the time of this research, the GitHub repository had no issues and each 0.1.0 release asset had one download attributable to the project's own post-release verification. There is not yet external uptake evidence to override the wait alternative ([0.1.0 release](https://github.com/raghavkandpal/parison/releases/tag/0.1.0), [GitHub issues](https://github.com/raghavkandpal/parison/issues)).

## What adjacent tools establish

These primary sources establish available capabilities, not user preference or a gap Parison has earned.

- DataComPy's current CLI can perform an ad hoc file comparison without a persistent recipe, accepts composite keys and per-column tolerances, prints a human-readable terminal report, writes JSON or HTML, exposes automation exit codes, and documents a GitHub Actions example. It also accepts CSV, TSV, Parquet, JSON/JSONL, cloud URIs, and Snowflake through supported backends ([official CLI documentation](https://capitalone.github.io/datacompy/cli.html)). Parison cannot differentiate merely by adding a terminal report, another file format, or a workflow snippet.
- DataComPy exposes typed report data for custom rendering and dashboards ([official report API](https://capitalone.github.io/datacompy/)). This weakens any claim that bundle history or custom presentation is unique.
- GitHub Actions already provides the generic persistence layer Parison needs: workflow artifacts retain files after a job and can pass them between jobs ([GitHub workflow artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)). The official upload action supports retention periods, missing-file failure, artifact digests, and immutable per-run artifacts; it also warns that artifact contents may be sensitive and excludes hidden files by default ([official `upload-artifact` repository](https://github.com/actions/upload-artifact)). Parison should compose with this native facility rather than build storage.
- GitHub already offers general workflow templates and organization-level reusable templates ([GitHub workflow-configuration documentation](https://docs.github.com/en/actions/concepts/workflows-and-actions/reusing-workflow-configurations)). A Parison example should therefore remain a copyable, product-specific reference rather than becoming a custom GitHub Action in 0.2.
- DuckDB and DataComPy already cover broader local input families. DuckDB documents CSV, JSON and Parquet readers with automatic detection, plus additional data sources; its import guidance recommends exporting source systems to Parquet or CSV when bulk export exists ([DuckDB import overview](https://duckdb.org/docs/guides/import/overview), [DuckDB data sources](https://duckdb.org/docs/current/data/data_sources)). New Parison connectors would expand type, credential, snapshot and network obligations without evidence that the current export boundary is the adoption blocker.

The external evidence supports a conservative conclusion: mature alternatives are broader and already automate well. Parison's defensible experiment is not breadth; it is whether explicit reviewed semantics plus portable, integrity-checked evidence make repeated migration decisions safer and easier.

### Why CI plus terminal orientation ranks first

It converts the already-validated one-off agent workflow into a falsifiable repeat-use experiment without changing comparison semantics. The difficult part is not writing YAML; it is demonstrating the correct control flow:

1. run Parison and retain its exact exit code;
2. upload the completed bundle even when the semantic result is `FAIL` or `INCONCLUSIVE`;
3. distinguish a missing/corrupt artifact from a comparison failure;
4. avoid publishing raw evidence from untrusted or public pull requests;
5. return the original Parison exit code after artifact handling.

A compact terminal summary makes the same run understandable in local agent transcripts and CI logs: outcome, completeness, essential counts, problems, sensitivity, bundle path, and an explicit reminder that `verify` checks integrity rather than semantic success. This is a rendering of canonical `result.json`, not a second result model.

## Proposed 0.2 scope

### Theme: repeatable evidence in CI

Ship:

1. A tested GitHub Actions reference workflow using the GitHub-hosted 0.2 release wheel, a committed recipe, user-provided baseline/candidate generation steps, and `actions/upload-artifact`.
2. Control flow that uploads a bundle for every published Parison outcome and then preserves exit codes `0`, `1`, `2`, `3`, and `130`.
3. Security notes for forked/public pull requests, raw sensitivity, artifact retention, and protected recipe changes.
4. A stable, concise human-readable `compare` summary on the terminal. Keep `result.json` canonical and do not change semantic results.
5. A smoke fixture or consumer-style test that runs the reference workflow's shell logic outside the project's own test workflow, so the example is executable documentation rather than illustrative YAML.

Publication fault tests may be added where deterministic and portable. They are trust work, not a reason to expand the visible feature set.

### Acceptance criteria

- For each outcome code, the reference flow uploads a bundle when Parison produced one and the job ultimately returns the original code.
- A missing bundle makes the upload step fail rather than silently succeeding.
- The uploaded directory passes `parison verify` after download.
- The workflow defaults to `summary` sensitivity and does not upload raw bundles for public-fork jobs in its documented configuration.
- Recipe changes are visible in review and the example explains why an untrusted candidate change must not relax its own gate.
- Terminal output states outcome, completeness, baseline/candidate/common/missing/extra/different/within-tolerance counts where available, sensitivity, and bundle path. It does not print keys or raw values in summary mode.
- `validate-recipe` and `verify` identify the validated recipe or bundle and explain what “valid” means without changing exit-code behavior.
- Existing 0.1 result and manifest schemas remain readable; comparison semantics and outcome codes are unchanged.
- One unfamiliar agent integrates the example into a clean fixture repository, and an unfamiliar engineer can determine the decision and retrieve/verify the bundle from the workflow run without maintainer help.
- At least one target user runs the same reviewed recipe a second time. Without this last observation, call the release technically complete but adoption unvalidated.

### Explicit non-goals

- No custom GitHub Action, bot, PR commenter, hosted service, or long-term artifact store.
- No automatic recipe approval, key inference presented as fact, tolerance inference, or silent schema policy.
- No JSON/JSONL, Excel, database, warehouse, object-store, or cloud-URI inputs.
- No report search/filtering, local web server, dashboard, or cross-bundle history.
- No changes to tolerance, null, identity, completeness, or PASS semantics.
- No claim that GitHub Actions is the only supported CI system; it is the first tested reference environment.

## Validation plan

1. Build a tiny external-style fixture repository with a protected recipe and scripts that deterministically produce `PASS`, `FAIL`, `ERROR`, and `INCONCLUSIVE`; simulate interruption separately where CI permits it without making the run nondeterministic.
2. Test the workflow's capture/upload/rethrow behavior for every exit code. Download each available artifact and run `parison verify` against it.
3. Put raw-value canaries into inputs and inspect logs, step summaries, artifact names, and summary bundles byte-for-byte. Repeat with a raw recipe only in a private trusted-branch scenario.
4. Give only the 0.2 README/reference workflow and fixture repository to an unfamiliar coding agent. Record interventions, incorrect exit-code handling, accidental skipped uploads, and security-policy changes.
5. Give the resulting Actions run to an unfamiliar engineer. Ask for approve/reject/inconclusive, the evidence supporting that choice, and verification of the downloaded bundle.
6. Ask three target engineers whether they will install the workflow in a second synthetic-equivalent or real sanitized migration. Measure time to first run, recipe setup time separately, integration changes, and whether the same recipe is run again.
7. If two independent users stall on recipe authorship, prototype `parison init` as a draft generator in a later 0.2.x or 0.3 experiment. Its output must mark user-supplied scope and key choices as unresolved and require review; do not infer policy that can produce a false PASS.

## Stop / wait alternative

The evidence is insufficient to justify a feature-led 0.2 today. A valid alternative is to make **no further product change** beyond the `0.2.0.dev0` marker while recruiting the first three external trials.

Choose wait if no target user commits to a second run or a CI integration. Choose the CI theme if at least one does. Choose recipe initialization instead only if observed setup shows recipe authorship—not installation, input production, or organizational review—is the repeated blocker. Choose report interactivity only after a user cannot answer a real investigation question from the existing summary/raw evidence. Choose a new format or connector only when a named workflow cannot reasonably produce CSV or Parquet and accepts the added support boundary.

The release decision should remain evidence-shaped: **0.2 is successful if it converts a correct one-off comparison into a trustworthy repeated practice.** Shipping more comparison surface without repeat use would not answer that question.
