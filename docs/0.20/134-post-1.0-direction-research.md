# Post-1.0 product direction research

Date: 14 October 2026

Status: **research recommendation**

## Question and boundary

This note compares three plausible directions after the 0.19/1.0 readiness work:

1. a narrow `.xlsx` values projection;
2. tooling that binds upstream extraction receipts to Parison evidence; and
3. adoption and workflow improvements around the existing comparison contracts.

The decision must preserve Parison's existing boundary: local inputs, deterministic execution, explicit policy, zero network and credentials, and no implication that a PASS establishes extraction truth or authorizes cutover. It also incorporates the format analysis in [the 0.19 non-CSV research](../0.19/124-non-csv-input-research.md) rather than reopening its format survey.

This is product-direction evidence, not proof of user demand, market size or willingness to pay. Sources are specifications, official documentation and repository evidence. External sources were accessed **14 October 2026**.

## Decision summary

Prioritize **adoption-led workflow improvement**, with one specific purpose: learn which existing workflow blocks repeated real use before expanding the input or attestation contracts. Do not begin post-1.0 with a new parser or a generic receipt schema.

The first slice should be a small, measured adoption cycle using the already shipped project initializer, schemas, integrations, catalog history, verified bundles, Statement handoff and consolidated command guide. Recruit or observe a few concrete migration/reconciliation workflows, record setup time and failure points, and make only bounded changes supported by that evidence. In parallel, collect actual source-owned extraction receipts as examples without ingesting or approving them.

Use two promotion gates:

- promote `.xlsx` only when multiple otherwise-suitable workflows are blocked by workbook export friction and their needed projection fits one common narrow contract;
- promote receipt binding only when at least two extraction systems provide stable, issuer-defined receipt semantics and a relying party can state a machine-checkable acceptance policy.

If both gates remain unmet, the correct post-1.0 result is maintenance and compatibility work, not a speculative feature release.

## Option 1: narrow `.xlsx` values projection

### Evidence

Office Open XML is not a flat table format. ECMA-376 defines document vocabularies, package representation and producer/consumer requirements across separate markup, packaging, compatibility and transitional parts ([ECMA-376](https://ecma-international.org/publications-and-standards/standards/ecma-376/)). A workbook reader therefore commits Parison to selecting a semantic subset of a package rather than merely decoding another delimiter.

The likely implementation dependency exposes useful but consequential behavior. `openpyxl` read-only mode lazily streams cells, must be explicitly closed and relies on workbook producers to report worksheet dimensions correctly; the official documentation notes that dimensions can be wrong ([openpyxl optimized modes](https://openpyxl.readthedocs.io/en/stable/optimized.html)). Its performance documentation says normal memory use can be roughly fifty times file size, recommends optimized modes, and notes that disabling external links avoids opening cached copies of linked worksheets ([openpyxl performance](https://openpyxl.readthedocs.io/en/stable/performance.html)). Its documented `data_only` behavior returns either formulas or the values stored when Excel last read the sheet, and it does not evaluate formulas ([openpyxl documentation](https://openpyxl.readthedocs.io/_/downloads/en/2.4/pdf/)).

These facts reinforce the 0.19 recommendation: a supportable reader would need an explicit worksheet and bounded rectangle/table, header and empty-cell rules, stored-value-versus-formula-text policy, date epoch and type mapping, presentation-state rules, hard package limits, parser/version evidence and adversarial fixtures. It must never recalculate, execute macros, follow links or imply that cached formula results are current.

### Design consequences

- Keep keyed, multiset and aggregate semantics unchanged; projection ends at the existing typed-row boundary.
- Make format and projection explicit in the recipe. Do not select the active sheet or infer an unbounded used range.
- Record the projection version and parser version in full evidence while preserving summary-safe redaction.
- Treat dependency upgrades as compatibility changes requiring golden workbooks and built-wheel CI on every supported Python/OS combination.
- Reject encrypted, malformed or resource-excessive packages and missing stored formula values deterministically.

### Threats

- ZIP/XML bombs, false worksheet dimensions, oversized shared strings and malformed packages can exhaust resources.
- Formula caches and external-link caches can be stale while still looking like ordinary values.
- Spreadsheet display formats, merged cells and date epochs can produce plausible but incorrect typed rows.
- Adding `.xlsm`, `.xlsb`, `.xls` or `.ods` by analogy would multiply parser and semantic surfaces.

### Non-goals

- workbook visual comparison, formula evaluation or recalculation;
- macro, external-link, query, pivot, chart or embedded-object execution;
- compatibility with legacy Excel or OpenDocument formats in the same slice;
- treating a workbook PASS as proof that formulas or source connections are correct.

### Promotion gate

Require at least two concrete target workflows where CSV/Parquet/JSONL/SQLite export is the documented adoption blocker, and verify that both fit the same worksheet/range, header, blank, formula and type policies. Until then, the implementation cost is supported by technical possibility rather than product evidence.

## Option 2: upstream extraction-receipt tooling

### Evidence

W3C PROV deliberately separates entities, activities and agents and can express that an activity used one entity and generated another. It is a general interchange model whose application-specific attributes and responsibility claims still need definitions ([PROV-O](https://www.w3.org/TR/prov-o/), [PROV overview](https://www.w3.org/TR/prov-overview/)). It supplies vocabulary, not proof that a claimed source snapshot existed or that an extractor observed it correctly.

The in-toto Statement model binds a typed predicate to immutable subjects by digest, but explicitly leaves predicate semantics to the producer and consumer. Its specification says subjects are matched purely by digest and requires a `predicateType` to identify what the predicate means ([in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md), [predicate specification](https://github.com/in-toto/attestation/blob/main/spec/v1/predicate.md)). Its predicate-template guidance requires fields, parsing rules, examples, versioning and migrations to be specified ([in-toto predicate template](https://github.com/in-toto/attestation/blob/main/spec/predicates/template/template.md)).

SLSA makes the same distinction in a mature domain: build provenance has a named build type, external parameters, resolved dependencies and run details, while accuracy and completeness depend on the builder identity ([SLSA build provenance](https://slsa.dev/spec/v1.2/build-provenance)). Verification must check the signature, trusted builder identity, predicate type and expected parameters rather than merely observe that provenance exists ([SLSA artifact verification](https://slsa.dev/spec/v1.2/verifying-artifacts)). SLSA Build L1 explicitly describes unsigned or incomplete provenance as useful for mistakes and debugging but trivial to forge ([SLSA build-track basics](https://slsa.dev/spec/v1.2/build-track-basics)).

Therefore, Parison can safely bind an exact receipt artifact to evidence, but cannot interpret `snapshot`, `watermark`, `query`, `complete` or issuer fields generically. A byte digest would prove which claim accompanied the run. It would not make that claim authenticated, comparable across source systems or true.

### Design consequences

- Keep receipts source-owned and separate from Parison's verification result.
- Before adding a receipt predicate, define its issuer, subject, extraction activity, input/output digests, stable source boundary, completion semantics, failure states and relying-party policy.
- Version predicate semantics. Unknown fields must not weaken a DENY or INCONCLUSIVE decision.
- Separate four checks: receipt byte integrity, issuer authentication, source-specific semantic validation and Parison result verification.
- Keep credentials, source APIs and remote verification outside core execution. Offline trust material may be supplied explicitly by a future integration.
- If early user value is only co-packaging, prefer a manifest-covered opaque receipt digest over a universal receipt schema, and label it as attachment identity rather than extraction validation.

### Threats

- Users may read “receipt present” as “exports are coordinated and complete.”
- Self-authored or unsigned receipts can restate recipe claims without adding evidence.
- Two sources can use the same field name for incompatible transaction boundaries.
- Issuer verification can pull Parison toward credentials, online identity systems, clock assumptions and revocation policy.
- Receipts can disclose source names, query text, table names, timestamps or infrastructure identifiers and therefore cannot enter summary-safe output casually.

### Non-goals

- defining one universal snapshot or watermark across databases, warehouses and SaaS exports;
- authenticating arbitrary issuers or contacting source systems in core execution;
- claiming that a signed receipt is accurate merely because its signature verifies;
- changing PASS into cutover approval.

### Promotion gate

Require stable receipts from at least two extraction systems, issuer-owned documentation of their semantics, and one consumer policy that can distinguish ACCEPT, DENY and INCONCLUSIVE without inspecting source data. Design a predicate only around the demonstrated common invariant; keep source-specific fields namespaced or opaque.

## Option 3: adoption-led workflow improvement

### Evidence

Parison already has the essential workflow surface: project initialization, strict schemas, preflight and policy lock, repeated rehearsals and catalog history, suites, deterministic evidence, verification, Statement handoff, cutover reporting, CI integrations and a consolidated command guide. Version 0.16 explicitly targeted fast project adoption, and the 0.19 work records one unfamiliar human completing the workflow without reported confusion. That is useful acceptance evidence, but it is not repeated adoption evidence, a comparison with users' prior workflow or proof that a new input format is the next constraint.

JSON Schema's official guidance encourages `title`, `description`, examples and related annotations because they make schemas self-documenting, while clarifying that annotations such as `default` do not themselves perform validation ([JSON Schema annotations](https://json-schema.org/understanding-json-schema/reference/annotations)). That matches Parison's safe pattern: improve authoring assistance while keeping runtime validation and explicit user approval authoritative.

Repository research already identifies real applications in migration, reconciliation, backfills and feature-pipeline parity, but also states that this is evidence of applicability rather than market demand ([real-world application research](../0.14/94-real-world-application-research.md)). The next uncertainty is therefore behavioral: which part of the complete workflow prevents a second real run?

### Smallest useful program

1. Select three bounded workflows from different contexts, such as a database migration rehearsal, warehouse transformation rewrite and financial/payout reconciliation. Use synthetic-equivalent data when real data cannot be retained.
2. Record the user's prior method, setup time, commands or automation needed, policy-review questions, errors, evidence-review time and whether they voluntarily repeat the run.
3. Capture every upstream artifact the workflow already produces, including export jobs and receipts, without asking Parison to interpret it.
4. Classify blockers before proposing features: input projection, extraction coordination, policy authoring, runtime/resources, investigation, evidence handoff or orchestration.
5. Implement only the smallest repeated blocker, with a predefined completion gate and the existing compatibility rules.

Likely low-risk fixes include better schema descriptions/examples, one checked integration recipe for a repeatedly observed workflow, clearer safe diagnostics, or removal of redundant steps. They are candidates, not a predetermined roadmap.

### Design consequences

- Treat adoption observations as evidence inputs, not permission to infer policy.
- Preserve strict JSON and stable CLI output; additions must not silently change old recipes or bundles.
- Measure the whole task, including extraction and policy review, rather than only comparison runtime.
- Record non-adoption and “existing script is enough” outcomes alongside successful runs.
- Keep workflow examples synthetic and connectors external.

### Threats

- Small samples can overfit the product to one team's terminology or infrastructure.
- Polishing the happy path can hide unresolved snapshot and completeness risks.
- User requests for automatic policy, repair or connectors can expand the trust boundary under the label of usability.
- Counting an assisted maintainer rehearsal as independent adoption would exaggerate evidence.

### Non-goals

- a hosted dashboard, interactive local server or new orchestration engine;
- remote database/SaaS connectors or embedded credentials;
- automatic key, tolerance, scope, exclusion or repair decisions;
- a broad CLI redesign before a repeated blocker is observed.

### Completion gate

Complete the cycle when three independent workflows have recorded outcomes and at least one is repeated by its intended operator or automation. Advance a feature only if the same blocker appears in at least two workflows or one workflow establishes a release-critical safety defect. Otherwise publish the findings and retain the current product surface.

## Recommended release sequence

### First: post-1.0 adoption evidence, not a feature promise

Use the first post-1.0 cycle to run the bounded program above. This is compatible with a patch/maintenance release if fixes are purely documentation or diagnostics; it does not require inventing a feature-bearing 0.20 release.

### Second: choose from evidence

- If workbook handling repeatedly blocks otherwise-valid workflows, implement `.xlsx` only under the narrow projection and threat controls already specified.
- If source-owned receipts expose a shared, verifiable boundary, specify a versioned extraction predicate and bind it by digest in a new Statement/predicate revision.
- If neither occurs, improve the repeated workflow blocker or make no semantic change.

### Why this ranks above the alternatives

`.xlsx` answers “can Parison parse another useful container?” Receipt tooling answers “can Parison bind another claim?” The unresolved product question is earlier: “which missing capability prevents trustworthy repeated use?” Adoption-led work answers that question while exercising the full released system and preserving optionality. It also produces the evidence needed to choose responsibly between the other two directions.
