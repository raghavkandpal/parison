# Independent review of the proposed Parison 2.2 train

Review date and source access: 23 October 2026. Baseline inspected: HEAD `37132a90ea09916c6a323b2034f20b9c06f31330`; latest tag `2.1.0`. `git diff 2.1.0 --stat -- src` was empty. `make context` showed the planning branch `docs/2.2-feature-research`; no unrelated work was reported. Read-only investigation; no implementation or tests were performed. This review was commissioned without author discussion history. Findings below distinguish repository facts from selection judgments. Repository links identify the inspected source files; line references in prose refer to the reviewed baseline.

## Verdict

Do not freeze a ten-feature commitment. The proposals largely identify real gaps, but the count obscures three different investments: making released engines usable in Workbench, introducing new portable evidence contracts, and expanding verification semantics. Select five substantial capabilities for 2.2: modern dataset evidence, suite authoring, recoverable suite execution, policy-change review, and suite series. Develop a complete reconciliation workflow next, including useful diagnosis and a real handoff contract, as one coherent capability group rather than three weakly connected promises. Explicit dataset assertions deserve a separate semantic train; archives and reconciliation comparison can wait.

This is a prioritization judgment, not evidence of customer demand or delivery duration. The accepted direction requires at least three substantial additions, not ten, and explicitly prefers coherent groups ([direction](../../docs/0.15/104-product-direction-and-release-arc.md)). The proposed ten are not inherently invalid counting: several can be separate capabilities. They nevertheless need not share one qualification/release boundary.

## Gap inventory made before evaluating proposals

The independent inventory was based on the released source, documentation index, and 2.1 contracts before reading 229/230:

1. **Evidence coverage lags input coverage.** Manifest v1 accepts only its closed format list, restricts JSON to receipt/supporting roles, and prohibits repeated physical paths and `(id, role)` pairs. Source identities support selectors and partition directories. This is a material verification gap, not a missing screen. [manifest normalization](../../src/parison/manifesting.py), [source identity](../../src/parison/inputs.py).
2. **Workbench cannot complete the suite lifecycle.** It runs a loaded suite but exposes neither retained execution workspace nor resume; CLI already has both. The authoritative loader already supports ordered cases, tags, limits, execution settings and explicit policy locks. Authoring and recovery are distinct operator decisions. [execution](../../src/parison/workbench.py), [runner](../../src/parison/suites.py), [loader](../../src/parison/policies.py).
3. **Policy evolution and repeated evidence are disconnected.** The existing diff service assesses recipe pairs, and existing ordinary-run analysis supports caller-ordered series. Workbench does not expose the first; the second does not accept suite parents. [policy diff](../../src/parison/evolution.py), [analysis](../../src/parison/analysis.py), [suite comparison](../../src/parison/suites.py).
4. **Reconciliation is an isolated CLI island with a deeper handoff gap.** Composed execution already exists. Workbench history filters to run/suite/shard. General Statement generation handles run/suite result layouts, not reconciliation. This is more than adding run/history routes. [composition](../../src/parison/reconciliation.py), [history](../../src/parison/workbench.py), [Statement snapshot](../../src/parison/evidence.py).
5. **Ordinary Workbench runs hide existing scale controls.** `execute_run` invokes preflight/comparison with defaults and exposes no engine, temporary-storage, or resource-limit arguments; suite cases already carry execution configuration. This is a credible alternative workflow improvement, with less semantic expansion than assertions. It needs a complete explicit execution-review capability to count as substantial, not merely a dropdown. [ordinary execution](../../src/parison/workbench.py), [case execution](../../src/parison/suites.py).

No gap above establishes a need for connectors, credentials, signing custody, repair, scheduling, inferred policies, fuzzy matching, or statistical drift. Those remain outside scope.

## Each proposal

| Proposal | Decision | Evidence and required reshape |
|---|---|---|
| 1. Workbench reconciliation | **Reshape; next coherent group** | Real gap, existing core semantics. Include useful failure explanation as part of completing this workflow; reuse shared services. Explicitly scope cancellation and handoff instead of assuming released paths suffice. `run_reconciliation` has no cancellation parameter; ordinary Workbench uses `InputCancellation`. A concise local report is possible, but using released Statement/report requires a new supported predicate/layout contract. See `reconciliation.py:920`, `workbench.py:93`, `evidence.py:596`. |
| 2. Modern dataset evidence | **Keep; rank 1** | Strongest core gap. Opt-in v2 physical/logical bindings are warranted; adding extensions to v1 would be wrong. Preserve the released partition identity algorithm and selector policy ownership. Manifest closed scope and logical selected-input membership are different claims: `_source_paths` excludes dot-prefixed children, while closed-manifest membership has its own enumeration rules. Specify both; do not silently redefine old membership. See `manifesting.py:92`, `inputs.py:431`, `inputs.py:450`. |
| 3. Policy-change review | **Keep, narrow** | Useful access to shipped `diff_policies`, not new compatibility semantics. Start with two explicit recipes and declaration, summary-first, with a separate schema-sensitive view. Drop optional draft-generation work unless there is a concrete edit operation: a deterministic comparison report is already a complete review outcome. Never create cross-policy history continuity or equate ACCEPT with approval. See `evolution.py:250`, `evolution.py:495`, `suites.py:41`. |
| 4. Recoverable suites | **Keep; rank 3** | Existing checkpoints mean this is feasible and valuable, but not zero-cost UI work. The runner explicitly rejects cooperative cancellation for `jobs != 1`; retain one job. Preview must reuse authoritative eligibility rules. Retention is sensitive custody of local evidence and must be explicit. See `suites.py:263`, `suites.py:385`, `workbench.py:124`. |
| 5. Suite series | **Keep after authoring/recovery** | Genuine new analysis service/artifact; not merely repeated pairwise screens. Restrict exact policies and selected complete executions; preserve caller order and explicit input changes. Avoid naming every count decrease “improvement”: different input bytes can explain it. Group IDs need case scope; counts can refer to different units across modes. See `analysis.py:238`, `suites.py:41`. |
| 6. Reconciliation comparison | **Defer; replace current promise** | Strict comparison is only useful for repeated runs of the same extraction declaration. Alignment contains receipt SHA, window, snapshot tokens/watermarks; reconciliation contains the alignment SHA. Thus a changed receipt necessarily changes alignment identity. The proposed changed-receipt-under-same-binding fixture is impossible under v1. Either market this as same-extraction comparison or separately research explicit cross-context observation reporting that does not claim parity. Do not strip these identity fields to force compatibility. See `reconciliation.py:97`, `reconciliation.py:389`. |
| 7. Reconciliation investigation | **Reshape into 1 initially** | Richer reason counts are already preserved: duplicate keys, orphan rows, ambiguous-parent rows, conservation counts. A useful diagnostic view belongs with the first complete reconciliation workflow. A new independently verifiable diagnostic artifact could later merit separate feature credit, but exporting a projection does not by itself establish substantial independent value. First strengthen/qualify authoritative validation of count shapes and reason derivation; see next section. `reconciliation.py:524`, `reconciliation.py:1045`, `reconciliation.py:1126`. |
| 8. Explicit assertions | **Defer to a semantic train** | A real gap: record validation checks parsing/keys, while this adds declared domains/ranges independent of parity. It fits explicit verification boundaries if strictly opt-in. However a standalone gate that cannot join suites fragments the principal workflow and introduces a new declaration, result, bundle, verifier, CLI and UI. Begin the next train with an explicit composition contract, not an uncomposable assertion island. Freeze raw-vs-normalized evaluation, nulls/empty input, invalid types, exact scalar bounds, and outcome vocabulary. `policies.py:766`, `docs/0.6/55-record-validation-contract.md`. |
| 9. Evidence archives | **Defer** | Dedicated safe pack/import is a genuine capability, not already shipped; existing directory portability is a workable current handoff. Archive ingestion adds an adversarial parser/publication boundary with modest demonstrated incremental user value. No need to couple it to manifest v2: archives should carry opaque verified bundle kinds, not reinterpret their sources. Prioritize correctly typed handoff for reconciliation/dataset evidence first. `evidence.py:479`, `evidence.py:596`. |
| 10. Suite authoring | **Keep; rank 2** | Directly completes the released 2.1 adoption path. Authoring should expose existing `execution` settings and explicit policy-lock choices as well as case order/tags/limits; no inference. Keep paths relative to eventual destination and use authoritative loader validation. A separate equivalent CLI builder is not necessary if exported JSON plus existing validation/list/run provides complete CLI consumption; justify any new CLI authoring surface independently. `policies.py:79`, `suites.py:302`. |

## Trust prerequisites that planning currently understates

**Reconciliation diagnostics must not promise stronger verification than the source verifier provides.** `verify_reconciliation_bundle` checks declared component membership, allows arbitrary nonnegative integer count keys for relationship/conservation components, then reduces their supplied outcomes. It does not close each count vocabulary or independently derive each component outcome from those counts there. This is a source-inspection fact, not an executed exploit or a claim that hashes authenticate issuers. Before new diagnostics explain verified counts, add hostile internally inconsistent fixtures, fixed count shapes, feasible arithmetic relationships, and outcome derivation for the existing result contract wherever compatible. Never claim that this re-executes against source data. Hardening itself does not count as a new product feature. [verifier](../../src/parison/reconciliation.py).

**Handoff is not currently universal.** `_evidence_snapshot` selects `suite-result.json` or `result.json`, then permits only keyed/aggregate/multiset ordinary contracts. Reconciliation uses `reconciliation-result.json`; dataset evidence has its own structure. A Statement/report expansion must define the policy/scope/coordination claims actually bound by each kind and preserve old bytes. “Concise handoff” cannot silently mean treating a relationship result as ordinary parity. This is a stronger replacement investment than archive packaging.

**Opaque IDs are not automatically confidential.** A deterministic hash over low-entropy public field/check names can remain guessable. Threat-model opaque component references as pseudonymous linkage unless their construction demonstrably prevents this; explicitly limit summary-safe promises to omitted names/values and the agreed disclosure contract. Do not accidentally disclose declaration fragments through reason text or default report labels. This is a security-design judgment, not a demonstrated current leak.

## Ranked train and completion gates

Recommended 2.2 train: five capabilities, each independently reviewable; no contingent sixth required for release.

1. **Modern dataset evidence:** prove physical-file/logical-binding v2 on structured selectors and partition sets. Gate: old byte fixtures unchanged; same workbook used twice; changed selectors/policy/partitions reject; no sources needed for preserved-evidence verification; cross-platform publication/size limits.
2. **Complete suite authoring:** explicit case composition and existing execution controls. Gate: author mixed modes, relocate/export/reload with matching intended identity; reference changes invalidate review; no execution during authoring.
3. **Recoverable suites:** authoritative reuse preview, retained-state lifecycle, restart/resume. Gate: prove actual reuse and stale-input non-reuse, safe cancellation, retention/abandonment, collision and post-publication catalog failure.
4. **Policy-change review:** exact recipe pairs and an explicit evolution declaration. Gate: rename, key, tolerance, exclusion and scope fixtures; summary disclosure assertions; accepted assessment cannot bypass exact-policy comparison.
5. **Suite series:** bounded, verified, explicitly ordered same-policy analysis. Gate: recurring/resolved/new failures, unchanged counts with changed bytes, mixed comparison modes, incomplete/tampered/mismatched cases; independent artifact verification and canonical fixtures.

Next strongest capability, outside the committed five: **complete reconciliation rehearsal and handoff**, combining 1 with the useful diagnostic portion of 7 and explicit Statement/report support. Gate first on verifier trust and cancellation, then on orders/lines/payments where parity passes but references/conservation fail. A stronger replacement for 6/9 is portable, correctly typed reconciliation/dataset evidence handoff; another practical alternative is reviewed explicit ordinary-run execution controls. Neither should become a quota filler.

Full `make check`, independent review, versioned documentation, preserved compatibility fixtures and exact-head Python 3.11–3.14 macOS/Windows/Linux built-wheel qualification remain required. A task trial must demonstrate that a user can distinguish agreement, assertion validity, evidence integrity, extraction coordination claims and cutover authorization. No operational approval is inferred from internal development gates.

## External evidence and limits

Primary sources accessed 23 October 2026:

- [dbt data tests](https://docs.getdbt.com/docs/build/data-tests) describes explicit non-null, uniqueness, accepted-value and relationship tests. This supports assertions as a recognizable operator capability; it does not establish demand for Parison's separate assertion bundle or warrant SQL execution.
- [Python tarfile documentation](https://docs.python.org/3/library/tarfile.html#extraction-filters) documents extraction filters and differing defaults across Python releases. This reinforces explicit validation/resource bounds across supported interpreters; “use stdlib” does not make arbitrary archive ingestion safe. No library defaults are recommended as a security boundary.

External precedent establishes feasibility patterns, not customer preference or correctness. No production workload study, benchmark, UI trial or feature implementation was performed. Unresolved decisions: manifest outer-bundle version; disclosure contract for opaque references; reconciliation Statement predicate; cancellation service boundary; assertion composition; scope/identity model for changing reconciliation windows. Resolve these in contracts and fixtures, not by quietly broadening old readers.
