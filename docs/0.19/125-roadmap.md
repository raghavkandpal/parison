# Parison 0.19 roadmap

Status: **release candidate**

## Theme: 1.0 readiness and compatibility

Parison 0.15–0.18 completed the accepted rehearsal, adoption, evidence-handoff and larger-keyed-comparison arc. Version 0.19 turns the qualitative 1.0 requirements into executable compatibility and workflow gates before expanding the input or dependency surface.

## Planned slices

1. [x] Freeze the [compatibility contract](126-compatibility-contract.md) for released recipes, schemas, bundles, CLI behavior and canonical artifacts.
2. [x] Seed an automated upgrade corpus with the immutable 0.1.0 run bundle and exercise verification, safe inspection, Statement projection and cutover reporting.
3. [x] Add original-release aggregate, multiset, suite-v1 and suite-v2 bundles to the upgrade corpus without regenerating them under current code.
4. [x] Exercise the complete migration/backfill command path under the installed wheel, from `parison init` through rehearsal history, suite execution, Statement export and cutover reporting.
5. [x] Consolidate the current keyed, aggregate and multiset measurements into an explicit, [machine-qualified performance envelope](127-performance-envelope.md) for memory and SQLite execution.
6. [x] Run and record a [direct-human workflow rehearsal](130-human-workflow-rehearsal.md); no usability gaps were reported.
7. [x] Define a checkable [1.0 release-readiness checklist](128-1.0-readiness-checklist.md).
8. [x] Consolidate the user guide, close the actionable performance gaps and prepare the [0.19.0 release checklist](133-release-checklist.md).

## Acceptance gates

- Every promised historical artifact remains readable and recursively verifiable under the current wheel.
- Compatibility tests use artifacts emitted by the named historical release, not fixtures regenerated by current code.
- Recipe meaning, comparison contracts, canonical encodings, exit codes and already-published schema identifiers do not change in place.
- The documented end-to-end workflow passes from a clean built wheel on Python 3.11–3.14, macOS and Windows.
- CI and evidence handoff retain strict identity, issuer, integrity and upstream-extraction boundaries.
- Performance claims name the machine, input profile, execution mode, accuracy result, time, peak memory and temporary storage measured.
- A direct-human rehearsal completes without undocumented repository knowledge.

## Deferred opportunity: additional inputs

The [non-CSV input research](124-non-csv-input-research.md) recommends a narrow, versioned `.xlsx` values projection and defers `.xls`, `.xlsb`, `.ods`, PDF, DOCX, OCR, email and generic logs to explicit upstream extraction. Native workbook support is not a 0.19 commitment: it should follow compatibility stabilization or concrete evidence that spreadsheet ingestion blocks adoption.

## Non-goals

- New input parsers, comparison semantics or execution engines.
- Automatic engine selection, remote orchestration or embedded credentials.
- Rewriting old artifacts into current schemas and calling that upgrade compatibility.
- Promising universal capacity from machine-specific measurements.
- Declaring 1.0 ready from automated tests alone.

This release operationalizes the 1.0 gates in the accepted [product direction and release arc](../0.15/104-product-direction-and-release-arc.md).
